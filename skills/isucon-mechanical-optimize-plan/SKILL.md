# ISUCON 機械的パフォーマンス改善(立案のみ)

対象は「振る舞い(レスポンス内容・アルゴリズムの結果)を変えない」パフォーマンス改善のみ。
N+1クエリ解消、インデックス追加、冗長なクエリの集約、無駄なアロケーション/直列化の削減など。
ソートアルゴリズムの変更やマッチングロジックの変更など、結果が変わりうる改善はこのskillの対象外。
**このskillはコードを一切変更しない。提案までで完結する。**

## 前提条件

- スコア優先度判定のため、isucon-manual-analysis skill の出力(またはmanual.mdの直接読み込み)でスコア計算式・重いエンドポイントの見当を把握する。
- **アプリケーションのソースコードのパス・言語は競技ごとに異なるため決め打ちしない。**
  リポジトリ構成(README、ビルド設定ファイル、既存のCLAUDE.md/AGENTS.md等)から
  実行時に特定する。

## 手順

0. アプリケーションのソースコードの場所と言語/フレームワークを特定する
   ハンドラ/コントローラ相当のファイル群がどこにあるかも合わせて把握する。
1. **候補の洗い出し(readonly)**: 手順0で特定したソースコードのハンドラ
   ファイル群を、Agent toolのsubagentで並列に解析し、以下のパターンを探す:
   - ループ内でのDBクエリ発行(N+1)
   - 同じデータを何度も引き直している箇所
   - RDBMSのスキーマ定義のインデックスでカバーされていない
     WHERE/JOIN列(インデックス追加の候補。既存インデックスの削除・見直しは
     このskillのスコープ外とする)
   - リクエストのたびに再計算しているが、書き込み時に増分更新できそうな集計
   - リクエスト処理中は一切書き込まれない(readonly な)テーブル・行を
     都度SELECTしている箇所(マスタ的なデータ。`postInitialize`/起動時に
     一度だけメモリに読み込んでソースコード側で保持する候補として検出する。
     対象テーブルが本当にreadonlyかどうかは、全ハンドラを横断してINSERT/
     UPDATE/DELETEの有無を確認してから判断する)
   - 不要なロック競合・直列化ボトルネック
   検出した各候補には「振る舞いが変わらないことの根拠」を明記させる。
   少しでも結果が変わりうるものは候補から除外する(アルゴリズム変更が
   要るものとして、別skill/人間の判断に回す)。
2. isucon-manual-analysis skill の出力を使い、各候補がどのエンドポイントの
   改善かを踏まえてスコア影響度を評価し、優先順位をつける。**各候補について、
   効果が及ぶエンドポイント(例: `GET /api/owner/sales`)を必ず特定する。**
   1つの改善が多数のエンドポイントにまたがる場合(例: 共通ミドルウェアや
   共通クエリヘルパーの改善)は、代表的なものを2〜3個ほど抜粋して列挙し、
   「等」を付けて他にも対象があることを示す(全列挙はしない)。
3. 候補一覧を人間に提示する(対象エンドポイント・振る舞い不変の根拠・
   見積もられるスコア影響・想定される変更規模・変更対象ファイル)。
   ここでコードは一切変更しない。実装するかどうか・どれから着手するかは
   人間が判断する。

## 既知の罠

- 「N+1解消に見えて実は結果が変わる」ケースに注意(JOINへの変更で行が
  重複/欠落する、NULL処理が変わる、順序が変わる、等)。疑わしいものは
  候補から外す。
- ベンチマーカーのソースは読まない。manual.md/ISURIDE.md相当/openapi.yaml
  相当のみを根拠にする。

## 出力フォーマット

候補一覧: 「対象箇所(ファイル・関数) → 対象エンドポイント(多数にまたがる
場合は代表例2〜3個+「等」) → 現状の問題 → 改善案 → 振る舞い不変の根拠 →
見積もりスコア影響 → 想定変更規模」
