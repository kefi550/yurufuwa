# ISUCON ログ解析

Webサーバ / RDBMS / アプリ(journal等)担当の Agent tool subagent を3並列で
fork し、自由記述findingsを集めて、manual.md の基準でスコア影響度を評価し
1本のレポートに統合する。**ミドルウェアは nginx / MySQL の可能性が高いが、
競技環境によっては異なることもあるため、パス・コマンドを決め打ちせず
実行時に確認する。**

## 前提条件

- manual.md のパスを必須引数として受け取る(当日配布されるもので、
  スキル内にハードコードしない)。渡されていなければ、まずパスを尋ねる。
- 対象ホストに ssh で接続できること。ホスト構成(アプリ/DB/Webが同居か分離か、
  台数)も競技ごとに異なるため、設定ファイル(env.sh相当)やユーザーへの
  確認を通じて実行時に把握する。
- **発動時点で対象ログ(access.log 等)がまだローテートされていないことを前提とする。**
  これは制約ではなく、単にローテート済みの場合を考慮しないという簡略化であり、
  ローテート検知や復旧処理はこのskillの範囲外とする。

## 手順

1. manual.md を読み、スコア計算式・クリティカルエラー条件・減点条件を把握する。
2. **ミドルウェア確認**: 各対象ホストに ssh し、まず nginx / MySQL が稼働している
   ことを前提に設定・ログの所在を確認する(`systemctl status nginx mysql` 等)。
   見つからない場合のみ、`systemctl list-units --type=service` や `ps aux`、
   パッケージマネージャ(`dpkg -l` 等)で実際に稼働しているWebサーバ・RDBMSの
   種類を特定し直す(例: Apache/Caddy、MariaDB/PostgreSQL)。
   自作アプリのプロセス名・systemdユニット名も合わせて特定する。
3. **ログの退避(固定化)**: 手順2で特定した、まだローテートされていない
   現在のログファイル(例: `/var/log/nginx/access.log`,
   `/var/log/mysql/mysql-slow.log`)について:
   a. 各ログの先頭行・末尾行からログの開始時刻・終了時刻を読み取る
      (nginxのltsvなら `time:` フィールド、mysqlスローログなら `# Time:` 行)。
      時刻は `YYYYMMDDThhmmss` 形式に正規化する。
   b. ssh先の `~/bench-logs/`(なければ作成)に `cp` で複製する。
      ファイル名は `<元のファイル名>.<開始時刻>_<終了時刻>` とする
      (例: `access.log.20260922T113000_20260922T113512`)。
      `mv` は使わない(nginx/mysqldがファイルディスクリプタで書き込みを
      継続しているため、reopenされるまで移動先に書き込まれ続けてしまう)。
   c. 以降の解析はこの複製ファイルに対して行い、ライブファイルには触れない。
      これにより後続のベンチ実行によるローテートの影響を受けない。
   d. journalは独自ローテート対象ではないため複製不要。手順aで得た開始・終了
      時刻をそのまま `journalctl --since <開始> --until <終了>` に使う。
4. 手順1〜3で把握した内容(manual.mdの要点、ミドルウェア種類とホスト対応、
   `~/bench-logs/` 内の複製ファイルパス、journal用の時刻窓)を踏まえ、
   3つの Agent tool subagent を**並列**に起動する:
   - **Webサーバ担当**: 基本は nginx を想定して、手順3で `~/bench-logs/` に
     複製したアクセスログを解析する(ライブの `access.log` は見ない)。
     nginxでなければ手順2の結果に応じて読み方を切り替える。ログ自体が
     無効化されていれば「集計不能」+「有効化すべき」をfindingsに含める。
     有効ならエンドポイント別レイテンシ・件数を集計する。
   - **RDBMS担当**: 基本は MySQL を想定して、手順3で `~/bench-logs/` に
     複製したスロークエリログを解析する(ライブの `mysql-slow.log` は見ない)。
     MySQLでなければ手順2の結果に応じて読み方を切り替える
     (例: PostgreSQLなら `log_min_duration_statement`)。無効なら同様に
     「有効化すべき」を提案する。有効なら遅い/頻度の高いクエリを洗い出す。
   - **アプリ/journal担当**: 手順2で特定したアプリ・関連サービスのsystemdユニットを
     手順3dの時刻窓で `journalctl -u <unit> --since <開始> --until <終了>` して
     エラー・再起動・レイテンシの兆候を洗い出す。
   - **ベンチマーカー担当**: プロンプトやファイルとして、ベンチマーカーの出力内容を与える場合がある。 
     ベンチマーカーの出力には、ベンチマーク中のエラーや警告や実行状況のヒントが記載されている可能性がある。スコアに対して不利な動きを検出したり、有利とするための改善アイデアを分析する。
   各subagentには manual.md の要点(スコア計算式・減点条件)も渡し、
   的外れな指摘を減らす。各subagentは自由記述でfindingsを返す
   (統一フォーマットは強制しない)。
5. 4つのfindingsが返ってきたら、それらを集約し、manual.md の基準で
   「直すとスコアにどれだけ効くか」を評価する。スコアへの影響が薄いものは
   優先度を下げ、各指摘に「なぜスコアに効くか」の根拠(manual.md該当ルール)
   を添える。
6. 影響度が高い順にソートした日本語レポートとして、そのままユーザーに返す
   (追加の集約フェーズや外部ツールは不要)。

## 既知の罠(確認時に注意すること)

- 設定ファイルの「スナップショット」(ローカルにpull/コピーしたコンフィグ)を
  鵜呑みにせず、実行時に対象ホストへ ssh して現物を確認する
  (実際のホスト構成やDB接続先が、ドキュメント上の記述と食い違っていた実例がある)。
- **このskillはログがまだローテートされていない状態での発動を前提としている。**
  既にローテートされていた場合の特定・復旧はこのskillの範囲外(発動が遅れた場合は
  ユーザーに確認するか、別途対応する)。
- 環境固有の既知のトラブル(証明書切れ等)はこのskillには埋め込まず、
  プロジェクト側の CLAUDE.md やメモリを参照する。

## 出力フォーマット

自由記述の日本語レポート。スコア影響度の高い順。各項目に
「観測事実 → 推定原因 → manual.md根拠 → 推奨アクション」を含める。
