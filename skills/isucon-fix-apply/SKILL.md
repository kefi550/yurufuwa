# ISUCON 修正の適用(Herdr並列)

ユーザーが承認した修正候補(1件でも複数件でも)を対象にする。対象は「機械的で
振る舞い不変な改善」に限らない — バグ修正(例: 決済リトライロジックの不具合)、
アルゴリズム変更(例: マッチング戦略の変更)、インデックス追加、クエリ書き換え
など、**この時点でユーザーが実装してよいと判断したものであれば何でもよい**。
**実装は候補ごとにHerdr worktree + Herdr agentで並列に進めてよいが、mainへの
着地(反映→デプロイ→ベンチ→commit→push)は1候補ずつ直列に行う。**

## 前提条件

- 承認済みの候補(isucon-mechanical-optimize-plan の出力、isucon-log-analysis
  で見つかった原因、またはユーザーが直接指定したもの)が対象。未承認の候補を
  勝手に実装しない。
- push.sh の実行、ベンチマークの実行はいずれも人間が行う。このskillはどちらも
  代行しない。
- **このリポジトリの実際のcommit運用に合わせる**: push.sh は `webapp/go/`・
  `env.sh` をrsyncするだけで、git commitを前提としない(未コミットの変更のまま
  反映・ベンチできる)。そのため、このskillは「先にmainの作業ツリーへ変更を
  反映してpush.sh→ベンチ」→「ベンチのスコア(またはpass/failと主要な警告/エラー)
  が分かってから、それを含めてcommit」という順序で進める。結果は人間に確認する
  (ベンチマークは人間が実行するため)。
- git remote への push は、commit後、必ず人間の明示的な許可を得た上で行う。
- isu1(実行環境)には同時に複数の変更を反映しない。着地は1候補ずつ。
- 振る舞いが変わる修正(アルゴリズム変更・バグ修正等)の場合は、**「何がどう
  変わるか」を実装前にユーザーへ一度明示し、認識を合わせてから着手する**
  (機械的改善と違い「結果が同じである根拠」では自己検証できないため)。
- **同時に開くworktree/Herdr agentは、フェーズA(実装中)・フェーズB(着地中)を
  合わせて最大4つまで。** フェーズBは1候補ずつしか進まないため、フェーズAだけ
  無制限に並列で作り続けるとフェーズBの手前で候補が溜まり続けてしまう。新しい
  候補のworktreeを作る前に、現在開いているworktree数(A+B)を確認し、4未満で
  あれば作成する。4に達している場合は、いずれかの着地(手順10)でworktreeが
  片付くまで新規作成を待つ。

## 手順

### A. 実装フェーズ(候補ごとに並列、ただしA+B合計4並列まで)

1. 承認された候補ごとに、現在開いているworktree数(A+B合計)が4未満であることを
   確認してから `herdr worktree create --branch <candidate-slug>` でworktreeを
   作成し、`herdr agent start <name> --kind claude --pane <root_pane_id>` で
   Herdr agentを起動する。複数候補があれば、4並列の上限まではこの手順を並列に
   行ってよい。上限に達している場合は、既存のworktreeが1つ片付く(手順10)まで
   新規作成を待つ。
2. 各Herdr agentへ `herdr agent prompt --wait` で、対象候補1つの実装を指示する:
   - その候補1つだけを最小のdiffで実装する(他の候補には触れない)。
   - 振る舞いが変わる修正の場合は、変わる範囲(対象エンドポイント・レスポンス・
     選択ロジック等)を実装前にプロンプト内で明示しておく(手順0で人間と合意
     済みの内容をそのまま伝える)。
   - ビルド確認(`go build ./... && go vet ./...` など、言語に応じた静的検証)。
   - diffを見ながら、意図した範囲以外(無関係なレスポンスフィールド・他の
     ハンドラ等)に副作用がないか確認する。
   - 問題なければそのworktree内のブランチにチェックポイントとしてコミットして
     よい(これは最終commitではない。最終commitはmainでベンチ後にスコア/結果
     入りで行うため、ここでのメッセージは仮でよい)。
   - 懸念点(副作用の可能性、要検証の前提など)があれば実装を止めず報告する。
3. 各Herdr agentから `herdr agent read` で実装結果(diff要約・検証内容・懸念点)
   を回収し、人間に提示する。

### B. 着地フェーズ(候補ごとに直列)

人間が「この候補から着地させる」と選んだものから、1つずつ以下を行う:

4. **候補ブランチを最新のmainにrebaseする**(worktree内で `git fetch`/
   `git rebase main` 相当)。他の候補が先に着地してmainが進んでいる可能性が
   あるため、squashする前に必ず最新のmainに追従させる。rebase中にコンフリクト
   が出た場合はworktree内で解消し、解消後は改めてビルド確認を行う(解消作業
   自体が実装フェーズの検証結果を無効化しうるため)。
5. rebase済みの候補ブランチを main の作業ツリーに反映する(例:
   `git merge --squash <candidate-branch>` で未コミットの状態でステージング
   する)。手順4でrebase済みのため、ここでのコンフリクトは基本的に発生しない
   はずだが、発生した場合は同様に解消し再ビルド確認する。**この時点ではまだ
   commitしない。**
6. push.sh の実行は人間が行う(このskillは代行しない)。ただし**実行を促す前に、
   チームメンバーとの競合(同時反映・isu1が今使用中でないか)を確認する許可を
   人間に求める。** 許可が得られたら push.sh の実行を人間にお願いする。
   push.shは作業ツリーの内容をそのままisu1にrsyncするため、未コミットの
   ままで反映できる。
7. ベンチマークの実行も人間が行う。このskillは実行しない。**人間から
   「ベンチマークが完了した」旨の報告と、そのスコア(またはpass/fail・
   発生した警告/エラー種別)を聞くまで、次の手順(commit)には進まない。**
   振る舞いが変わる修正の場合は特に、クリティカルエラーや警告が新たに
   増えていないか確認する(必要なら isucon-log-analysis skill の再利用も
   検討する)。結果が悪化していた場合は、原因がこの候補にあるのか切り分けた
   上で、commitせず変更を破棄するかどうかを人間に確認する。
8. 結果を確認できたら、その結果を含めてmainにcommitする(このリポジトリの
   慣習: `<変更内容の要約> score <点数>`、例
   `owner/chairsの集計をインデックスで高速化 score 1580`。pass/failや
   警告件数など、スコア以外に特筆すべき結果があればメッセージに含めてもよい)。
   これがこの候補の最初で唯一の実質的なcommitになる(worktree内のチェック
   ポイントcommitはsquashによってまとめられる)。結果が芳しくない場合は、
   commitするかどうか・変更を維持するか破棄するかを人間に確認する
   (未コミットの変更を勝手に破棄しない)。
9. commit後、**人間の明示的な許可を得た上で** main を git remote へ push する。
10. 着地が終わったら、そのHerdr worktreeを片付ける(`herdr worktree remove`
    など)。次の候補について手順4に戻る。

## 既知の罠

- 実装(A)は並列でよいが、着地(B)は必ず1候補ずつ。isu1には同時に複数の変更を
  乗せない。
- 複数候補のブランチが同じファイル(例: 同じハンドラファイル)を触る場合、
  マージ時のコンフリクトが起きやすい。コンフリクト解消時は「両方の変更の
  意図を保ったまま副作用が増えていないこと」を都度確認する。
- 「いきなり実装させる」とコンパイルエラー等が放置されるリスクがあるため、
  手順2の検証(ビルド・diffレビュー)を省略しない。
- push.sh実行・ベンチマーク実行は人間の作業であり、このskillは代行しない。
  push.sh実行は促す前にチーム競合確認の許可を得る。git pushはベンチ完了の
  報告と人間の許可の両方が揃うまで行わない。
- **squash前に必ず候補ブランチを最新のmainにrebaseする**(手順4)。他の候補が
  先に着地している場合、rebaseせずにsquashするとmainの最新状態を取りこぼし
  たり、不要なコンフリクトが起きたりする。
- **mainへの取り込みは必ず `git merge --squash` を使い、通常のマージコミット
  は作らない。** この候補についてmain上に残るcommitは手順8の結果入り1個だけ
  にする(worktree内のチェックポイントcommitはsquashで履歴に残らない)。
- 振る舞いが変わる修正は、機械的改善と違って「diffを見れば安全とわかる」わけ
  ではない。実装前に変更範囲をユーザーと合意し、着地後のベンチ結果(手順7)を
  機械的改善の場合以上に注意深く確認する。

## 出力フォーマット

実装フェーズ完了時(候補ごと): 「対象候補 → worktree/ブランチ → 変更した
ファイル/diff要約 → 検証済み事項 → 懸念点(あれば)」

着地フェーズ完了時(候補ごと): 「squash取り込み結果(コンフリクトの有無・
解消内容) → ベンチマーク完了確認の状況・結果(スコア/pass-fail/警告種別)
→ 実際のcommitメッセージ → git push可否の判断 → 実施したアクション」
